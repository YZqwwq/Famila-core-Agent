# 原生 HDSI 分段延迟测试

2026-11-15。本轮保留完整叙事、原生提示词、顺序提交和消息合并/打字配置；不启用 fast。用户已认可上轮情境下的聊天质量，本轮只检查耗时。

## 方法

新增 `scripts/hdsi-latency-acceptance.cjs`。通过实际 HTTP POST /messages 发送三轮连续日常聊天，记录首个 text_delta 和完整 SSE 响应结束时间。代理把原生非流式模型请求转换为服务端流式传输以观测首个非空 content，收齐完整输出后重新包装为普通 JSON 交给 HDSI。原生内核不会收到半成品，也不会提前投递。

这会改变模型 API 的传输选项，因此不是普通非流式入口的逐字等价复现；提示词与原生提交路径保留。TTFT 包含本地代理、网络、服务端排队和 prefill，无法在客户端进一步拆分。生成阶段包括流式传输等待，不代表纯 GPU 解码时间。

先运行 `node scripts/hdsi-latency-acceptance.cjs --fixture`，本地模拟首内容等待 40ms、后续等待 80ms，三轮均正常提交和投递。之后运行不带参数的真实测试，总上限 6 请求、每次 2048 输出 token、30 秒模型超时。实际 3 请求，qwen3.8-max，关闭思考；独立数据目录。未更改生产配置。

真实报告：`evals/companion_zh/reports/hdsi-latency-live-1794688284470/results.json`。该目录还保存了实际请求和完整输出，不包含 API 密钥。

## 结果

| 轮次 | 模型请求前 | 请求至首 content | 首 content 至完整输出 | 模型完成至可见回复 | 首回复总耗时 |
|---|---:|---:|---:|---:|---:|
| 1 | 2.19s | 1.01s | 8.45s | 0.10s | 11.76s |
| 2 | 2.07s | 1.28s | 14.00s | 0.08s | 17.43s |
| 3 | 2.06s | 1.07s | 11.08s | 0.08s | 14.29s |

输入 token 分别 6138 / 7150 / 8316，缓存 token 分别 0 / 4096 / 5120；输出 token 分别 373 / 562 / 465。按完整输出 token 除以首 content 后时长估算，约 40–44 token/s。缓存命中后首 content 等待仍约一秒，不能用这三条推导缓存的因果收益。

回复分别为“这么晚才忙完啊”“煮面吧”“[emoji: 🙂]”。本轮不对表情标记渲染或聊天质量重新评分。

模型前约 2.1 秒与默认 2 秒消息合并窗口一致，但没有内部钩子精确拆出合并、上下文读取等子项，不能把它全当纯队列等待。模型后只约 0.1 秒，说明本次短回复的模拟打字没有额外造成几秒等待；本地固定输出测试曾观察到 1.3–2.25 秒的模型后等待，因此不能外推所有回合。

## 判断与下一步

本次持续生成/流式传输占总耗时约 72%–80%，首 content 等待约 7%–9%。本次没有后台整理请求，也没有下一条消息与前一回合重叠，不能用它验收后台整理锁竞争或突发排队。

既然保留叙事篇幅，优先对同一份捕获请求做模型服务速度对照，再测缩短消息合并窗口。模型服务对照必须控制模型、参数、输出量、缓存和采样变化；不能只比较两次总耗时便宣称供应商更快。暂不改生产流程，也不重新启用会跳过状态提交的旧 fast。
